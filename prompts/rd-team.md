# 制作・R&D: 実物を見ながら改善する

Taskのworkflow.mode=rdのとき、prompts/run-team.mdと併せて使う。主担当が仮説/制作/実装/テスト、品質確認担当が実物と計測を評価する。基本はこの2役。追加の専門家や並列workerは必要な部分だけ。

## 開始条件
- ユーザーの「ここからR&Dで」「品質を見ながら繰り返して」、または提案への承認をPLAN/HANDOFFに記録する。対象Taskだけに適用する。
- AIが自分でrdにしない。提案するときは理由を示し、承認を待つ。
- 始める前に、主担当と品質担当 (原則別出自) の候補AI・モデルをconfig/ai-team.jsonとcheck-budgetの結果 (残り枠) から示し、ユーザーに「この組み合わせでよいか」を確認する。決まったら workflow.approval (日時とユーザーの言葉) と workflow.team {lead, quality} に agent / model / origin を書く。途中でモデルを替える時も確認し直して記録する。
- 新規3D/動画は要望・シナリオ・完成イメージを先に整理する。プロジェクトの制作スキルや原本保護規則を守る。
- モード選択は生成、GPU、課金、素材再利用/上書き、配布、pushの許可を追加しない。既に許可された範囲は聞き直さず、未承認の拡大だけ確認する。
- 主担当/品質担当と代替をTEAMに一度記録する。品質担当は原則主担当と別出自で同じ担当を継続する。毎回編成を聞かない。同じ出自しか使えない場合は独立性の不足を明示しユーザー判断を仰ぐ。

## Taskの契約
work_type (例: blender-3d / video / ue-cpp) と別にworkflowを持たせる。
scripts/orchestration/fixtures/rd-task.jsonをコピーし、placeholderを実際の合意内容に置き換えてtemplateフラグを除く。未記入の例は起動を拒否する。

- mode: rd
- criteria: 観察できる合格条件の配列。必須の不具合修正と好み/追加改善を区別。
- baseline: 比較元の成果物/commit/hash/計測、または最初の基準データを取る具体的な計画。
- controls: 比較中の固定条件。3DGSならカメラ・解像度・Gaussian数・品質設定・場面・機材/負荷、動画なら尺・fps・seed・素材・出力条件など。
- max_iterations / max_minutes: 合意した試行回数と累積作業時間の上限。例の3回/60分は自動の許可ではない。主担当が工程全体の開始時刻・試行数・消費時間を記録して守る。
- iterations_used / minutes_used: 主担当が記録する累積消費。初回は0。各試行後と再開時に実績から更新し、上限以上なら次の試行の起動を拒否する。観察・報告だけのTaskはnormalとして別に作る。値の真正性や実時計による自動停止は検証しない。
- stop_conditions: 改善停滞、同じ欠陥の再発、比較不能、意見対立など、ユーザーへ戻す条件。

python scripts/orchestration/team_control.py workflow --task-file <path> で形式チェックする。JSONの整合性だけを調べ、基準の妥当性・実際の許可・経過時間は自動検証しない。
委任workerにも同じ契約を渡す。残り上限と今回の試行番号をconstraintsに明記し、独自に反復させない。

## 1回の反復
1. 主担当が仮説・変える点・期待する改善を記録する。基準がなければ先にbaselineを作り、改善済みとは主張しない。
2. 許可された制作/実装/実験を行い、新しい固有の出力先へ保存する。良好結果を保持し、原本や前の試行を上書きしない。
3. 入力・commit/hash・設定・固定条件・実行コマンド・計測・経過時間・成果物の絶対パスを.ai/reports/配下の試行reportへ残す。映像は時刻/フレーム、3Dは視点を特定する。
4. 品質担当は実際のレンダー/フレーム列/必要な再生と計測を見て、条件を項目ごとに判定する。静止画1枚で時間方向のちらつきや音声同期を合格にしない。観察手段が足りなければUNREVIEWED。
5. 指摘には固定ID、試行/成果物、場所/時刻、症状、重要度、根拠、再確認方法を付ける。主担当は採用と修正を記録し、閉じた項目も影響範囲を回帰確認する。
6. 次の試行前に回数・累積時間・停止条件を確認する。達成なら報告してIn reviewへ。未達で上限内なら修正へ。上限/停滞/同じ不具合の反復/好み変更/意見対立はpendingで比較と選択肢をユーザーへ返す。

## 品質状態とコードレビュー
- 完了・成功と報告する前に finish-check を通す (品質担当の quality {agent, model, origin, status, report} と、コード変更の review.reports が必要。コードを変えない計測だけの試行は important=false と review.skip_reason)。品質がVERIFIEDでなければ成功と言わない。
- 指摘はOPEN → FIXED_PENDING_QC → VERIFIED。修正だけではVERIFIEDにしない。観察できない項目はUNREVIEWED。
- コードテスト/NullRHI/バイト一致はGPU・視覚・実機性能の合格ではない。別々に報告する。
- normalの「修正後は再レビューしない」はコード・手順レビューの制限。rdの実物の品質再評価には適用しない。
- rdのコード変更にも通常の独立レビュー規則を適用する。重要変更は独立2モデル。品質評価で代替しない。
- レビュー対象commit/成果物を固定する。同時に書く係を動かす時は別worktree/出力先を使い、レビュー対象を変更しない。
- 品質担当を継続してもworker_done受理後はrelease/reuse/retainの規則を守る。次回は前回reportと指摘IDを引き継ぐ。workerはユーザーへ直接聞かない。

## 切替・再開・終了
- normalへ戻す前にR&D契約と実績をPLAN/HANDOFF/試行reportへ保存し、Taskのworkflowはmode=normalだけにする。rdへ戻す時に元の契約と累積消費を復元する。指摘・試行数・時間・基準を保持し、normalのテスト合格で品質指摘を閉じない。上限をリセットしない。
- 条件を変えるなら新baselineを明記する。Gaussian数や品質を下げて同品質の高速化と主張しない。
- 交代/再開はPLAN/HANDOFFと試行reportから復元し、live/unknown workerを重複起動しない。
- 報告は達成条件、未確認、採用成果物と比較根拠を示す。確認待ちはreview、判断待ちはpending。Doneと評価は明示承認の規則に従う。
